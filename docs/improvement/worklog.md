## 01 来源和构建条件（2026-11-17）

现象：远端 main 的 Qt 主窗口未接入较新整机的摄像头/考勤；本地整机代码含网络、视觉与控制逻辑。当前目标需要收敛，不能以历史描述当作本轮结果。

选择：创建独立 worktree，保留两个原目录及原 Git 工作区已有未跟踪文件；以 e015ddd 为可追溯基准。只提取本地整机中的业务需求与失败机制，不复制整套未验证架构。

命令：`git -C D:\vm\embedded-learning-github worktree add -b codex/imx6ull-local-monitor D:\vm\github\smarthome-imx6ull e015dddc4c8d661db2c4fadc179762b7a431539b`。

结果：worktree 建立；来源文件哈希和 Linux 主机信息保存在 `evidence/2026-11-17-local-monitor/00-baseline/`。现有 Linux VM 有 GCC 9.4/CMake 3.16/Python3，未找到 Qt 开发工具；可用磁盘约 2.4 GiB，没有为此安装系统包。

## 02 Windows Qt 评估（2026-11-17）

Windows 注册表旧 Qt 5.14.2 路径 D:\qt 不存在；实际可用的是 D:\qt_install 下的 Qt 6.11.1 和 MinGW 13.1 64 位。

选择：优先使用既有 Windows 工具链，不额外安装 Linux Qt。Qt 6 原生构建使用 C++17；业务核心保持 C++11，Qt 5 板端构建单独验证。

命令：`qmake -query`；用 `01-windows-qt/probe.pro` 生成 Makefile，`mingw32-make -j2`；`QT_QPA_PLATFORM=offscreen` 执行探针。

判据：编译/运行退出 0，按钮信号计数为 1，窗口抓取非空。

实际：通过，JSON 为 `qt_version=6.11.1, pointer_bits=64, clicks=1, rendered=true, pass=true`。完整输出在 `01-windows-qt/`。

限制：证明 Windows 工具链与 Qt Widgets 可用，不证明 Qt 5.12.9、ARM ABI、Linux 驱动或实物动作。

## 03 场景收敛与采集/报警核心

原始现象：本地整机中 DHT11 的三次读取失败重试包含 3×1200 ms 等待；后续光照/测距在同一线程执行。报警分支还依赖由识别字符串推导的旧状态。不能只修改描述而保留相同依赖。

取舍：独立新主程序 `app/`；旧 `02-应用层QT/` 与较新整机保留，不把历史视觉代码当作新主链。新程序以 `core/monitor.*` 定义状态和有效期，`core/sampling.*` 分别调度输入，`core/devices.*` 区分模拟与真设备，`core/linux_devices.cpp` 使用原有字符设备契约。Qt 线程只通过 bridge 排队交付样本，UI 为唯一业务状态所有者。

采集一次只尝试一次，下一周期再试；保留失败计数与时间。采用少量独立线程隔离阻塞设备，未宣称单核计算吞吐提升。新增输出接口反馈，写失败不显示为接口成功。

判据：核心覆盖布撤防、100 次重复高电平不重复启动、静音/重触发、环境回差、数据失效、独立原因和错误输入；受控 DHT 阻塞期间光照继续返回；可取消替身停止后线程全部回收。

实际：Windows 7 个核心场景通过。首轮完整 Qt 工作流与拒绝隐式模拟通过。命令与原始日志见 `02-windows-r1/`；具体数值不是 ARM 板端指标。

## 04 PIR poll/read 契约

现象：Git 基准应用使用 poll，驱动 fops 没有 .poll，注释里的“等待 1 秒”不能单凭用户态代码成立。应用启动时输入已经为高电平也需要明确快照。

修改：`01-驱动层/hc_sr505.c` 添加 poll_wait/就绪判断、首次快照、单打开者 EBUSY；读操作通过互斥/自旋锁协调，用户拷贝失败时保留最新待消费状态。应用非阻塞读取，发现就绪与 EAGAIN 不一致时报告 EPROTO 并退避，不隐式忙轮询。

命令：在独立 Linux 临时目录执行 `tools/verify-linux.sh`。源包两端 SHA-256 一致；后续单独驱动传输也核对哈希。

失败：R1 核心和工具已编译，模块在未使用的 ARM 专用头处失败。修正：移除未使用的体系结构头，R2 成功。R1/R2 都保留。

实际：R2 核心 7 场景、ASan/UBSan 通过，5.4 x86_64 内核头下模块编译通过。未加载该模块，未执行硬件契约工具。4.1.15/ARM 编译和实际 GPIO 行为待恢复环境。

## 06 测试和来源复核

发现原隔离测试虽然有闸门，但没有先确认 DHT 线程确实进入等待，理论上可能在该线程尚未调度时满足光照计数。修正测试：等待进入闸门后再计额外 4 次光照更新，最后释放并退出。

Windows 复核 CTest 3/3，Linux R3 原生与 ASan/UBSan 核心测试均通过。测试源码传输哈希核对；未重复无改动的驱动构建，沿用 R2 编译与对应源指纹。最终源文件、二进制和日志指纹及机器可读结果随 evidence 保存。

本轮结论是源码行为和主机替身验证成立。下一步只有在设备与旧 SDK 条件确认后，才执行 board-restoration.md 的目标编译、接口和物理测量；无需为当前阶段重建摄像头/考勤环境。

复核输出错误传播时发现：关闭输出失败虽然写了日志，原进程仍可能退出 0。修正主程序退出码，并增加专门的模拟关闭输出故障测试，要求同时出现 shutdown_output_error 和退出 1。

实际：`07-shutdown-review` 的构建和 CTest 4/4 通过，正常模拟启动脚本仍通过。最终阶段结论以此轮及 Linux R3 为准；旧轮次仍可追溯。

最后的敏感模式检查首次因正则以连字符开头、未使用 -e 而报参数错误，未据此判无匹配；改为显式模式参数后重新检查，结果保存在 review.json。
